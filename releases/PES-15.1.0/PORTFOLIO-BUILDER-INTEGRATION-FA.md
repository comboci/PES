# طرح اتصال PE-15 به NSP Portfolio Builder

## هدف

استفاده از PE-15 به‌عنوان سیستم ثبت دانش، تصمیم، شواهد و وضعیت توسعه پروژه، بدون تغییر Canonical PES-14 و بدون تحمیل مهاجرت به نرم‌افزارهای موجود.

## یافته‌های واقعی در GitHub

در بررسی فایل `project evolution/Project-Evolution-V1-PES-14.json` از مخزن `comboci/NSP-Portfolio-Builder` در `main` در تاریخ ۲۰ نوامبر ۲۰۲۶، نمونه جدید شامل **۱۲۵ رکورد** در ۱۵ مجموعه، **۱۰ Scope**، **۳۱ Task** و **۳۵ Observation** بود. همه تسک‌ها فاقد `priority` و همه Observationهای بررسی‌شده فاقد `observed_at` بودند. یکتایی Record IDها، ارجاعات داخلی بررسی‌شده و ارجاع پیش‌فرض Retrieval مشکل آشکاری نداشت. Blob SHA در زمان بررسی: `29ce3b4d309581a6974d10ea366155c8e8b4f243`.

این بررسی از طریق دسترسی خواندنی GitHub انجام شد؛ تغییرات خودکار بعدی ممکن است آمار و SHA را تغییر دهند. **کد Python نسخه ۱۵ در محیط محلی روی کل فایل جدید مخزن اجرا نشده است**؛ تست مهاجرت و SQLite در این بسته روی Fixture نماینده و ۷۳ تست خودکار انجام شده‌اند.

## استراتژی پیشنهادی: Side-by-side

ساختار پیشنهادی در مخزن برای مرحله Integration، بدون بازنویسی:

```text
project evolution/
  PES-14-STANDARD.md                      # دست‌نخورده
  PROJECT-EVOLUTION-START-HERE-PES-14.md    # دست‌نخورده
  Project-Evolution-V1-PES-14.json          # دست‌نخورده و فعال برای عامل‌های فعلی
  pes15/                                     # مسیر جدید، مستقل و Opt-in

```

اجرای ساعتی فعلی که به `PROJECT-EVOLUTION-START-HERE-PES-14.md` اشاره می‌کند باید تا تصمیم صریح مالک به همان فایل وفادار بماند. PE-15 به‌صورت موازی توسعه و ارزیابی می‌شود؛ **هیچ Job موجودی بی‌اجازه به نسخه ۱۵ سوئیچ نمی‌شود**.

## گام‌های Integrate

1. آخرین `main` را دریافت و SHA فایل PES-14 را ثبت کنید.
2. بسته PE-15 را در پوشه جداگانه Extract کنید و تست‌ها را اجرا کنید.
3. ابزار `tools/evaluate_portfolio_builder.py` را با `--source` به فایل حقیقی PES-14 و با `--output-dir` به پوشه کاملاً جدید اجرا کنید.
4. گزارش `integration_report.json` را بررسی کنید: نبود حذف/تغییر رکوردها، تعداد استثناهای تاریخی، هش مبدا قبل/بعد، خطاهای Schema و صحت Backups.
5. یک آداپتور مستقل PE-15 برای UI/Backend Portfolio Builder تعریف کنید. لازم نیست همه اطلاعات محصول به PE منتقل شود: PE دانش پروژه است؛ پایگاه SQLite محصول منبع دیتای کاربری برنامه است.
6. مسیر نوشتن PE-15 را فقط از طریق Validator + `CanonicalStore.commit(...)` ارائه کنید؛ هر عامل AI Revision + SHA را دریافت کرده و باید تعارض را صریح حل کند.
7. در UI، وضعیت `implemented`، `verified` و `accepted` را با منابع و رکوردهای جداگانه نمایش دهید؛ داده تاریخی «نامعلوم» را به موفقیت تبدیل نکنید.
8. قبل از فعال‌سازی عمومی، Crash/Power-loss، Backup/Restore، دو Process همزمان، سنجش Performance، بررسی امنیت و تست‌های تعاملی محصول اجرا و تأیید شوند.

## قرارداد ذخیره‌سازی پیشنهادی

- **Canonical Store نسخه ۱۴:** فایل JSON فعلی در GitHub، برای مصرف‌کننده‌های قبلی.
- **Canonical Store نسخه ۱۵:** یک دیتابیس SQLite مستقل تحت مسیر مدیریت‌شده جدید؛ هر تغییر یک Revision جدید.
- **Adapter:** CLI یا Python API PES-15؛ مستقیماً بدون Validation در DB دستکاری نکند.
- **Context API:** `pes15.retrieval.context(snapshot,scope,contract_id)` خروجی read-only شامل منشأ و هشدارها.
- **System of Record محصول:** SQLite مربوط به پروژه Portfolio Builder (پروژه‌ها، قالب‌ها، تصاویر و صفحات) خارج از PES-15 باقی می‌ماند؛ قاطی‌کردن این دو ذخیره‌گاه توصیه نمی‌شود.

## معیارهای پذیرش قبل از مهاجرت عملی

- محتوای همه رکوردهای تاریخی، شناسه‌ها، ارجاعات، Scopeها، وضعیت‌ها و Provenance بدون تغییر واقعی بماند.
- هیچ Task جدید بدون `priority` و هیچ Observation جدید بدون زمان معتبر وارد Canonical نشود.
- دو نویسنده روی یک Revision باعث Lost Update نشوند؛ یکی Commit کند و دیگری `Conflict` بگیرد.
- تست نگهداشت/نسخه‌ها و Online Backup موفق باشد.
- خروجی Context موارد نامعلوم و Evidence/Acceptance ناقص را مشخص کند.
- نسخه ۱۴ و Automations آن بدون تغییر همچنان اجرا شوند.

## محدودیت‌های فعلی

این بسته به‌تنهایی کد Portfolio Builder را تغییر نداده، در `main` Commit نکرده، تست Build/Runtime واقعی برنامه را اجرا نکرده و تأیید مالک محصول را دریافت نکرده است. محیط Local Demo مستقل است. پیاده‌سازی Adapter در خود برنامه یک تسک Integration جداگانه است.


### الحاقیه اختیاری PES-15.1 — نمایش بخش‌های مستقل در HTML

این الحاقیه صرفاً راهنمای ادغام آینده است؛ در کد HTML یا سورس Portfolio Builder تغییری نمی‌دهد.
در صورت ساخت UI جدید، پنج بخش مستقل تحلیل، اولویت‌بندی، اصلاح/اجرا، بررسی و پذیرش باید مستقیماً از `workflow.phases` داده بگیرند.
Badge اولویت/رنگ، وضعیت تکمیل اصلاح نیست. `task_progress.deliverable_complete` وضعیت خروجی *نوع خاص آن تسک* است و نباید به‌عنوان تأیید تست یا مالک نمایش داده شود.
رکوردهای PES-14 فعلی در همین وضعیت باقی می‌مانند؛ نمایش Workflow ناموجود باید «نامعلوم» باشد، نه انجام‌شده.
